# FPGA Ramp 的 Python 上位机改造方案

本方案依据当前目录内的 RTL、XDC、Vivado 工程文件及保存的实现报告制定。尚未连接开发板、重新综合或测量 DAC 输出；报告可能与板上实际烧录版本不同。本文是设计方案，所列新增模块和 Python API 尚未实现。

**后续实施说明：第一版已在本目录实现。** 本文保留设计历史，实际能力、入口和限制以根目录 `README.md`、`docs/协议-v1.md` 和 `docs/验收记录.md` 为准。实际协议采用固定 32 字节帧，首版为 64 段参数执行器；时钟与引脚管理已加入 Python 子页面。下文的 256 段、任意点表、可变长度帧等仍属后续设计，不代表本次已交付能力。

2026-09-10 实施更新：新固件已将参考时钟 50 MHz 倍频至 200 MHz，核心和两路 DAC 数据/转发时钟共享此时钟；内部布局布线和时钟模型仿真已通过，见验收记录。下文第 10 节保留早期 50 MHz DAC 兼容方案作为设计历史。当前波形最短更新间隔为 80 ns、设置步进 5 ns；DAC 器件和板级 IO 尚未实测。跨 FPGA 仍采用平台适配器方式。

## 1. 结论与分工

推荐保留现有 Artix-7 FPGA 与 DAC，在电脑上增加 Python 上位机，通过通信接口下载参数或波形。FPGA 继续负责外部触发、计时、波形执行和 DAC 输出。

日常使用可不再打开 Vivado：在 Python 界面编辑、预览、下载、布防和运行实验。开发 FPGA 固件时仍需要 Vivado 综合、实现和生成 bitstream。普通 Windows Python 程序不能保证逐点输出的确定时间；不能用 `time.sleep()` 循环代替硬件波形时序。[Python 官方说明](https://docs.python.org/3/library/time.html#time.sleep)

```mermaid
flowchart LR
    UI[Python 界面与实验脚本] --> COMP[波形编译与参数校验]
    COMP --> LINK[USB 转 UART]
    LINK <--> CFG[FPGA 命令解析与配置缓存]
    CFG --> SEQ[FPGA 序列执行器]
    TRIG[外部触发] --> SYNC[同步与边沿检测]
    SYNC --> SEQ
    SEQ --> DAC[现有两路 10 位 DAC 接口]
    SEQ --> STAT[状态与事件记录]
    STAT --> CFG
```

## 2. 当前工程事实

| 项目 | 核查结果 | 对改造的意义 |
|---|---|---|
| 器件 | `Assistant_FPGA.xpr` 指定 `xc7a35tfgg484-2` | 可继续使用现有 FPGA；当前方案不要求更换开发板 |
| 系统时钟 | XDC 的 `sys_clk` 周期 20 ns，即 50 MHz | 当前 ramp 使用此时钟，内部计时网格为 20 ns；这不是模拟输出精度保证 |
| 顶层 | `Assistant_main.v` | 在此增加通信、配置和新执行器连接 |
| 当前控制 | `vio_0` 的 11 个输出探针 | 起止值、步长、时间、模式和复位均经 VIO 设置 |
| 输出 | `dipole_ramp[9:0]`、`fm_value[9:0]` | 两路数字输出码范围 0–1023；电压范围和极性须通过 DAC 资料及标定确定 |
| 触发 | F13 为 ramp，F14 为 FM，XDC 配置 LVCMOS33 | 保留外部触发；电气兼容性需核对实际接线 |
| 工作模块 | 顶层实例化 `dipole_ramp_main` | `dipole_ramp_fsm.v` 虽在工程中，但没有被当前顶层实例化 |
| 保持过程 | 当前 `ramp_type=0` 在输入保持高电平时向终值运行并保持，下降沿启动返回 | 没有独立的 `hold_time`；高电平宽度还包含前一段 ramp 所用时间 |
| 方向 | 当前 `ramp_type=0` 数字运算为减小到 end、再增大到 initial | 不能直接把代码模式名称等同于物理 ramp up/down；需考虑模拟电路是否反相 |
| FM | 每个有效上升沿推进一个扫描点，首次触发输出初始码 | 可保留此兼容模式，随后增加与 ramp 的统一时序 |
| 通信 | 顶层没有 UART、以太网等上位机接口 | USB 下载口不能直接假定为可用 COM 串口 |
| 状态反馈 | 当前 VIO 配置为 0 个输入探针、11 个输出探针 | 现有 VIO 不能反馈运行状态或测得的模拟波形 |

当前时间参数宽 29 位，若按 50 MHz 时钟计，最大参数约 10.74 s；实际执行时长还受代码的点数和比较逻辑影响，不能直接等同于精确 ramp 时长。

## 3. 两条实施路线

### 路线 A：Python 调用 Vivado Tcl，经 JTAG 控制已有 VIO

连接方式：Python → 常驻 Vivado Tcl 会话 → Hardware Manager / hw_server → JTAG → VIO。

适合先实现现有参数的表单化、方案保存、批量改参。AMD 官方提供设置 `OUTPUT_VALUE`、调用 `commit_hw_vio` 更新探针的流程。[AMD 官方命令文档](https://docs.amd.com/r/en-US/ug835-vivado-tcl-commands/commit_hw_vio)

操作顺序应为：禁止新触发并进入配置状态 → 设置所有参数 → 提交 → 校核配置 → 解除复位并使能。现有 `config_ready=0` 会把输出带回初始码，配置时更新初始码也可能改变输出，所以此模式只适合在已停止的实验间更新。

`vio_rst_n` 在当前 ramp RTL 中实际上按高有效参与复位，不能依名称当成低有效。上位机应屏蔽这个历史命名差异。

局限：电脑仍依赖 Vivado 工具链和 JTAG；只改界面不能增加 FPGA 尚未支持的段序列、独立保持时间或任意波形。当前 RTL 也没有软件触发输入，不能假设写 VIO 即可产生软件触发。新增执行状态反馈需要修改 RTL/VIO。

因此，此路线适合作为过渡验证，不作为复杂波形的最终架构。

### 路线 B：Python + USB-UART + 通用波形执行器（推荐）

先核对板卡原理图：若板载 USB-UART 已连接 FPGA，则复用；否则选择两个可用、可接出的 FPGA IO，通过匹配其 Bank 电压的 USB-UART 转换器连接 TX/RX，并使用实际 GND 引脚共地。不能把代码中的 `gnd0/gnd1` 常低 GPIO 当作正式接地端，也不能直接连接 RS-232 电平。

不在缺少原理图时指定 UART 管脚。XDC 里被注释的其他 DAC 管脚也不能自动视作可用空闲管脚。

首版通信采用 115200 baud、8N1，足以下载段参数；大量波形点下载可在验证收发误差和适配器能力后提高到约 1 Mbaud。Python 使用 pySerial，需设置读写超时，并按完整协议帧处理分片到达的数据。[pySerial 官方 API](https://pyserial.readthedocs.io/en/stable/pyserial_api.html)

固件稳定后，可在确认板卡配置 Flash 型号及启动模式后固化，实现上电运行、Python 连接即用。

## 4. 波形能力和执行约定

建议同时提供两种触发模式：

1. **完整序列模式**：外部上升沿启动，自动执行 ramp up → 定时 hold → ramp down。后续触发下降沿不改变本次运行。
2. **电平门控模式**：上升沿启动第一段，到目标后保持；下降沿从当前实际输出码启动返回。如果第一段未完成即下降，不先跳到目标值。

首版规定：只在 ARMED 状态接受开始触发；运行中新的开始触发忽略并计数；完成后进入 DONE，连续重复次数在 FPGA 内计数。门控模式所需的下降沿作为阶段切换事件单独处理。布防时输入已高，建议必须先看到低电平再接收新上升沿，避免误启动。

基本状态为 IDLE → ARMED → RUNNING → DONE；运行段类型决定线性变化、保持或查表。STOP 转入预设返回过程，ABORT 输出已配置的中止码。两者语义分开；实验设备需要硬件联锁时，联锁独立于串口命令。

| 能力 | 实现位置 | 首版建议 |
|---|---|---|
| 起始码、目标码、终止码 | Python 设置，FPGA 锁存 | 支持 |
| 上升、保持、下降独立时间 | 段表 + FPGA 计时 | 支持 |
| 多级 ramp、多平台保持 | 多段顺序执行 | 支持，先限制 256 段 |
| 同一序列重复 | FPGA 循环计数 | 支持 |
| 参数扫描 | Python 生成下一组，等待完成后下载并布防 | 支持；组间不保证固定延迟 |
| 组间严格固定时间的扫描 | 扫描表预下载，FPGA 内循环 | 后续支持 |
| S 曲线、指数、自定义点列 | Python 计算，FPGA BRAM 查表 | 第二阶段 |
| 两通道同步 | 共享时基和触发事件，分别保存输出码 | 第二阶段；要求更严时需核查两 DAC 的模拟延迟 |
| 状态记录 | FPGA 返回段号、输出码、计数、错误 | 支持；返回码不是模拟实测值 |

示例方案（均为数字码，未作电压标定）：

| 阶段 | 起点 → 终点 | 时长 |
|---|---|---|
| 上升 | 100 → 800 | 20 ms |
| 保持 | 800 → 800 | 100 ms |
| 下降 | 800 → 100 | 50 ms |

完整序列模式下总长 170 ms，由一次外部上升沿启动，不需要电脑在三个阶段之间发送指令。

## 5. 段参数与任意波形的组合设计

**线性段与保持段使用参数描述。** 长时间保持只占一条指令，避免把整个实验展开成大量采样点。段记录建议固定 32 字节、版本化，包含类型、通道掩码、更新次数、起止码和预计算参数；首版 256 段约 8 KiB，最终字段布局在协议实现时冻结。

选择 `K` 个核心时钟周期作为更新间隔，`dt=K/core_clk_hz`。新架构目标为 200 MHz，因此 K=200 对应 1 µs，K=1 对应 5 ns 的内部时间网格。K 的最小值由执行器吞吐能力、DAC 适配层和实际器件验证共同决定，不默认支持每 5 ns 输出一个新模拟采样点。对持续时间 T，Python 计算 `N=round(T/dt)` 并显示量化后的实际时间；线性段要求 N≥1，零时长跳变使用显式 SET 指令。

为消除实时除法，Python 对幅差 D=abs(end-start) 预计算 `q=D//N`、`r=D%N`。FPGA 每次更新按方向增加/减少 q，并用余数累加器分配额外的 1 个码值变化，经过 N 次更新精确到达终值。误差累加和比较使用扩展位宽，最终输出限幅至 0–1023。段起点在开始时生效，第 N 次更新到终值；下一段边界复用该时刻，不重复增加一个间隔。

这能让总时长不依赖幅值差是否整除步长，并使内部累计时间误差受明确的量化规则控制。32 位更新次数在 1 µs 间隔下可覆盖约 4295 s；更长时长通过多段保持或更宽计数扩展。

**复杂曲线使用 BRAM 表。** Python 负责公式求值、重采样、幅度校验和 10 位量化，FPGA 只按已下载的间隔取样。初始可以配置每通道 4096 个 16 位存储点，两通道约 16 KiB；若做双缓冲，点表约 32 KiB，另加描述表、FIFO 和状态资源。当前保存报告中 BRAM 使用为 0/50 个 Tile，但最终仍要重新综合确认布局和资源。

4096 点在 100 kS/s 下约覆盖 40.96 ms；长保持应使用 HOLD，长平滑线性变化应使用参数段。16 KiB 双通道点表在 115200 baud、8N1 下纯数据传输约 1.42 s，在 1 Mbaud 下约 0.164 s，尚不包含协议开销。下载时间发生在布防前，不限制随后 FPGA 的本地播放速度。

## 6. 通信协议与配置一致性

建议二进制帧：`A5 5A | version:u8 | command:u8 | sequence:u16 | payload_length:u16 | payload | CRC16`，多字节字段小端，CRC 使用 CRC-16/CCITT-FALSE，覆盖 version 至 payload，长度按字节计。首版 payload 上限 512 字节。解析器需要超时复位、长度校验和错误后重新寻找帧头。

| 命令 | 功能 |
|---|---|
| GET_INFO | 读固件/协议版本、时钟、通道数、段数和点表容量 |
| WRITE_CONFIG | 写触发模式、更新间隔、输出限值和停止行为 |
| WRITE_SEGMENTS / WRITE_WAVEFORM | 带方案 ID 和偏移地址分块下载 |
| COMMIT | 校验完整性及数值范围，在允许状态下原子切换配置 |
| ARM / DISARM | 布防或取消等待 |
| SOFT_TRIGGER | 软件开始；精确外部同步仍使用硬件触发 |
| STOP / ABORT | 受控返回或中止 |
| GET_STATUS | 返回状态、段号、输出码、触发计数、配置 ID、错误码 |

每条响应携带原序号和 ACK/NACK。重发带副作用的命令必须去重；例如重复收到同一 ARM 或 SOFT_TRIGGER 不能重复启动。配置使用 active/shadow 两套数据，首版仅允许在 IDLE/DONE 时 COMMIT；一旦 ARMED 或 RUNNING，active 保持不变。串口写参数不能直接连到正在执行的输出逻辑。

GET_INFO 同时返回 `board_id`、`core_clk_hz`、`dac_clk_hz`、`min_update_ticks`、`dac_bits`、`max_segments`、`max_waveform_points` 和 `feature_flags`。Python 按设备实际能力编译；不把 200 MHz 或 10 位写死在通用上位机中。固件若未实现某一能力必须明确拒绝，不静默降频或改变时长。

下载成功的含义是 FPGA 已完成校验并返回 COMMIT ACK；上位机收到 ACK 后才显示“可布防”。状态每秒读取约 10–20 次即可，通信放工作线程，GUI 只处理显示。

断开电脑后，已布防或运行的序列是否继续，做成明确配置。建议实验运行默认完成当前已提交序列；需要失联停止的场景启用 FPGA 心跳超时返回。上电、复位与错误输出码须作为设备配置明确保存。

## 8. RTL 修改位置与已有问题

| 文件/新增模块 | 工作 |
|---|---|
| `Assistant_main.v` | 加 UART 端口、配置与状态总线，保留现有 DAC 引脚；VIO 如保留则明确控制权 |
| `dipole_ramp_main.v` | 用通用序列执行器替代实时除法和分散的模式分支 |
| `frequency_modulator_main.v` | 先保留外部逐次触发功能；补范围校验，随后接统一时基 |
| 新增 `uart_rx/uart_tx` | 串口接收与发送 |
| 新增 `command_parser`、`config_bank` | 协议、配置校验、原子提交和响应 |
| 新增 `sequence_engine`、`waveform_ram` | 参数段执行、重复计数、查表输出 |
| 新增 `trigger_sync`、`status_regs` | 触发同步、事件与运行状态 |
| `Assistant_main.xdc` | 经原理图核对后增加 UART 管脚；补全 DAC 时序与触发 CDC 约束 |

应随重构处理的已知事项：

1. 保存的 `Assistant_main_timing_summary_routed.rpt` 日期为 2025-12-09，WNS=-81.603 ns，118 个 setup 失败端点，明确写明时序未通过。最差路径从 VIO 终值寄存器到 ramp 输出，数据路径延迟 101.495 ns、245 级逻辑。源码中连续组合除法是重点排查对象，最终归因及改善要以重新实现报告为准。
2. `points` 仅 10 位，而全幅差 1023、步长 1 时表达式可产生 1024，发生截断；新执行次数和码值必须使用不同位宽。
3. `total_time/points` 可得到 0，随后 `flag_time-1` 存在下溢风险；新编译器和 FPGA 两端都校验持续时间。
4. `ramp_type=0` 中触发边沿与电平分支可能同拍执行，对同一寄存器重复非阻塞赋值；新 FSM 必须定义单一优先级。当前固定减法/加法也不适合任意端点顺序。
5. 当前参数直接影响运行中组合逻辑；新配置必须先锁存再执行。
6. FM 的累加应校验终点，避免 10 位回绕。ramp 的中间加减同样使用扩展位宽再限幅。
7. 现有报告列出 20 个输出缺少 output delay。当前 DAC 时钟直连 sys_clk、数据在 sys_clk 边沿更新，需要依据 DAC 采样边沿、建立保持要求和板级走线核查输出寄存器/转发时钟相位，并补约束。
8. 外部触发同步器添加适当的 ASYNC_REG 属性及 CDC 约束，测量固定流水线延迟和异步相位引起的一个时钟级量化差异；最小触发脉宽需依据实际采样设计验证。不能把 20 ns 时钟周期宣传成端到端 20 ns 响应保证。

## 9. 实施顺序与验收

**阶段一：确认硬件与基线。** 确认开发板、DAC/模拟输出模块、UART 可用引脚、触发电平和最小脉宽、目标时间尺度；测量当前典型波形，记录数字码与物理量方向。重新生成基线报告，区分历史报告与当前源码结果。

**阶段二：最小可用闭环。** 完成 UART、配置寄存器、独立三段状态机及状态读取，Python 先提供 CLI/SDK。验收示例 100→800/20 ms、保持 100 ms、800→100/50 ms；外部触发后本地自动完成，反复触发行为一致。

**阶段三：日常使用界面。** 加连接管理、参数校验、预览、JSON 保存、运行状态和日志。冻结通信协议，确认上电及停止行为后验证 Flash 启动。

**阶段四：复杂实验。** 增加多段、循环、点表、参数扫描及双通道同步。根据实际容量和下载耗时再决定是否需要更快通信。

必要验证包括 RTL 仿真中的端点相等、正反向、最短段、零/越界参数、短触发、运行中重触发、配置未完成、重复命令、CRC 错误和串口断连；上板用示波器检查时长、单调性、边界连续性、触发延迟和两通道偏差。时序验收要求 setup/hold 满足、无未解释 CDC 问题且 DAC IO 约束完整。测试期读取的数字码不能替代模拟波形测量。

开始具体接线及可烧录实现前，仍需获取开发板型号/原理图、DAC 型号与输出范围、上升/保持/下降的典型及最短时长。方案本身不依赖先更换硬件。

## 10. 200 MHz 倍频与跨 FPGA 适配

### 10.1 当前时钟 IP 与修改目标

现有 `ip_clk_wiz.v` 实例化 Clocking Wizard，生成 250 MHz、100 MHz、180° 相移的 100 MHz、500 MHz；顶层的 ramp 与 FM 仍连接 `sys_clk`，这些倍频输出没有驱动它们。`locked` 没有导出供主逻辑复位使用，内部 `rst_n` 也没有被使用。

更明显的是：当前时钟 IP 的 `.reset(!vio_rst_n)` 为高有效，而 ramp 的 `reset0 || vio_rst_n` 将同一信号按高有效复位处理。不能继续复用这种互相矛盾的复位定义。

新方案建立独立 `clock_reset_adapter`，统一外部复位为高有效 `reset_req`，输出 `clk_core`、`rst_core`、`clock_locked`。PLL/MMCM 的复位由参考时钟域或板级复位电路管理；核心逻辑复位包含未锁定条件，异步置位、在目标时钟域同步释放。命令触发的业务复位不复位负责其接收的整个时钟链。不能直接用 `!locked` 持续反馈到 MMCM reset，造成永远无法锁定。

锁定后建议通过至少三级目标时钟域复位同步器释放 `rst_core`，同步器按厂家要求标记。失锁进入禁止接受触发状态，输出行为通过板级 DAC 适配器定义；若时钟停止，不能依赖该停止时钟完成一个同步返回过程。精确启动及失锁行为需上板验证。[AMD 时钟模块使用指导](https://docs.amd.com/r/2023.1-English/ug1387-acap-hardware-ip-platform-dev-methodology/Using-Clock-Modifying-Blocks-MMCM-XPLL-and-DPLL)

当前 Artix-7 使用 Clocking Wizard / MMCM 将 50 MHz 生成 200 MHz。本次 Vivado 2023.1 对 `xc7a35tfgg484-2` 成功生成的参数为：输入分频 D=1，反馈倍频 M=20，输出分频 O=5，VCO 为 1000 MHz，输出为 200 MHz。其他器件仍需由对应 Clocking Wizard/PLL 配置流程校验，不跨器件硬套。无需保留未使用的 250/500 MHz 输出。

### 10.2 核心时钟、更新间隔与 DAC 时钟

首版倾向让 UART、命令解析、配置和波形执行都在同一个 200 MHz 核心域，低速工作使用 clock enable，减少不必要的跨时钟通信。UART 波特率参数必须据实际核心频率重新计算。

外部触发经过核心域同步器检测，以 5 ns 网格捕获；仍包含同步流水线延迟、输入相位量化以及后续执行/输出延迟，不能宣称触发至模拟输出为 5 ns。

DAC 输出时钟单独配置。现有硬件未知能否接收 200 MHz，第一阶段以原 50 MHz DAC 接口速率为兼容目标，并使输出更新与其采样边沿对齐。200 MHz 核心可以通过每四拍一次的使能配合输出时序；如需输出 50 MHz 时钟，使用专用时钟/DDR 输出资源并核查相位和建立保持时间，不用普通组合门拼接时钟。此配置下 DAC 更新网格仍至少为 20 ns，而非 5 ns。

如果 DAC、后级模拟电路和板级布线均满足更高速率，再将 DAC 适配配置提升到 100/200 MHz。200 MS/s 下相邻数字采样的更新率也不能替代模拟带宽、建立时间和精度指标。

若后续为降低功耗使用独立低速控制域，命令和配置跨域通过异步 FIFO 或带确认的稳定数据握手传送，不能给每一个多位参数独立加两级同步器。来自同一 MMCM 的相关时钟应保持正确时序关系，不能无依据设置为异步时钟组来消除失败路径。

### 10.3 时间参数迁移与 200 MHz 时序闭合

用户方案统一保存秒/ms/µs 等物理时间。Python 根据 GET_INFO 返回的频率和可用更新间隔编译为计数，保持更换 FPGA 前后实验时长一致。

原来 50 MHz 下的直接周期计数，换成 200 MHz 后需要乘 4 才保持时长不变。原 29 位计数在 200 MHz 下只覆盖约 2.684 s；新执行器采用可配置的更新间隔及足够宽的段计数，明确拒绝溢出。32 位更新次数在 1 µs 间隔下仍覆盖约 4295 s，但在 5 ns 间隔下约为 21.47 s。

200 MHz 的周期预算为 5 ns。现有保存报告在 20 ns 周期下已失败，不能只改时钟连接。实施时先消除组合除法，再分离配置校验与运行数据路径，预取下一段描述，控制组合逻辑深度；必要的流水线必须把延迟计入段边界，并以 `min_update_ticks` 对上位机公开限制。双端口 RAM 的读延迟和多通道输出延迟需要对齐。

XDC 的外部 `create_clock` 仍为 20 ns，因为物理输入仍为 50 MHz；200 MHz 是 MMCM 的派生时钟，由 Vivado 根据时钟资源推导。不能把输入约束直接改为 5 ns 充当倍频。通过 `report_clocks` 检查派生周期 5 ns，并执行实现后的 setup/hold、CDC、DAC IO 时序检查。

### 10.4 可移植目录与边界

```text
rtl/common/                    通用 UART、协议、寄存器、执行器、触发逻辑
rtl/platform/xilinx_7series/    当前 Artix-7 时钟、复位、RAM/IO 适配
rtl/platform/<family>/         其他器件系列的时钟及资源适配
boards/<board_id>/             器件、晶振、引脚、电平、DAC 参数与约束
scripts/vivado/                Vivado 工程与 IP 重建脚本
scripts/<vendor_tool>/         其他厂家构建脚本，按实际目标增加
host/                          共享 Python 界面、编译器、协议
```

| 层次 | 可以复用的部分 | 更换器件时需要处理 |
|---|---|---|
| Python | 波形编辑、保存、实验脚本、协议 | 读取新设备能力；下载/烧录工具由板级配置决定 |
| 通用 RTL | 计数、状态机、UART、协议、插值 | 参数与性能约束，必要时调整流水线 |
| 时钟 | `clock_reset_adapter` 接口约定 | AMD MMCM/PLL、Intel PLL 或目标厂商专用 IP |
| 存储 | 统一读写接口和显式读延迟约定 | 优先可推断 RAM；不能一致推断时使用适配包装 |
| DAC IO | 统一码值及更新接口 | ODDR/DDR 原语、转发时钟、引脚、电压、采样相位 |
| 构建 | 统一板级参数概念 | AMD 用 Vivado；Intel 等使用相应厂商工具链 |

例如 Intel 的 PLL 也提供复位和锁定状态，但具体 IP 及端口依器件族而异，不能直接综合 Xilinx 原语。[Intel PLL 官方说明](https://www.intel.com/content/www/us/en/docs/programmable/683775/current/reset-64028.html)

“兼容不同 FPGA”在本项目中定义为源码架构和上位机可复用，每种板卡单独生成 bitstream、单独约束、单独验收。不是同一 bitstream 到处烧录，也不保证所有低端 FPGA 都能在 200 MHz 下达到相同吞吐。首个验证目标为 `xc7a35tfgg484-2`；其他目标必须在提供准确型号后加入构建矩阵并实测，不能先标记为已支持。
